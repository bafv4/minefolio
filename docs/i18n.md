# 多言語対応（i18n） 仕様書

## 概要

日本語（既定）と英語に対応する。メッセージカタログは**全キー英訳済み**。新しい文言は日本語だけ先に足されることがあるため、未翻訳キーは日本語へフォールバックする仕組みを残している。

ガイド本文・プロフィール文など**利用者が書いた内容は翻訳対象外**（そのまま表示する）。
これを機械翻訳で補う機構は `docs/translation.md`（土台のみ実装済み・表示は未実装）にある。

---

## 対応ロケール

| ロケール | 表示名 | 状態 |
|---|---|---|
| `ja` | 日本語 | 全キー。**フォールバック先の基準** |
| `en` | English | 全キー英訳済み（カタログ外のハードコード文字列は下記「まだ日本語のまま残っているもの」） |

単一情報源は `app/lib/locale.ts` の `SUPPORTED_LOCALES`。

---

## 表示ロケールの決まり方

`resolveLocale(request)`（`app/lib/locale.ts`）が次の順で決める。

1. **Cookie `minefolio_locale`** — 切替UIで利用者が明示的に選んだ値。最優先
2. **`Accept-Language`** — 未選択の訪問者向けの自動判定。q 値の降順で最初に一致した対応言語
3. **既定（`ja`）**

判定は `root` ローダーで一度だけ行い、`<html lang>` と `LocaleProvider` へ渡す。SSR とクライアントで同じ値になるため**ハイドレーション不一致が起きない**。

### 旧実装から直した点

`app/lib/i18n.ts`（削除済み）の検出には2つの不具合があった。`app/lib/__tests__/locale.test.ts` が両方を回帰テストしている。

- Cookie を `/minefolio_locale=([^;]+)/` で正規表現照合していたため、`xxxminefolio_locale=en` のような**別名 Cookie にも一致**していた → 名前を完全一致で比較する
- Accept-Language を `includes("ja")` で見ていたため、`en-US,en;q=0.9,ja;q=0.5`（英語優先）でも**日本語と判定**していた → q 値を解釈して優先度順に見る

## 文言の追加・参照

キー実体は `app/lib/messages/pages-ja.ts`（日本語・全キーの基準）と `app/lib/messages/pages-en.ts`（英語）。

- **日本語のキーを追加 → 英語は任意**。`pages-en.ts` は `PartialMessages<typeof PAGES_JA>` 型なので、キー名の打ち間違いは型検査で落ちるが、未翻訳は許される
- 未翻訳キーは `t()` が日本語を返す。**キー名が画面に出ることはない**
- 空文字（`""`）は「意図的な訳」として扱う（日本語の助数詞「人」など、英語では付けないもの）。`t()` は `undefined` 判定でフォールバックする

### コンポーネントからは `useT()`

```tsx
import { useT } from "@/hooks/use-locale";

export function Something() {
  const t = useT();
  return <h1>{t("guides.pageTitle")}</h1>;
}
```

**`t()` を直接 import して呼ぶと常に日本語になる**（モジュールレベルの純粋関数でリクエスト文脈を持たないため）。コンポーネントでは必ず `useT()` を使う。

### ローダー / meta からは locale を明示する

フックを使えない場所では、そのスコープの先頭でロケールに束縛した `t` を作る。呼び出し側の書き方はコンポーネントと同じになる。

```ts
// ローダー / アクション
export async function loader({ request }: Route.LoaderArgs) {
  const t = createTranslator(resolveLocale(request));
  throw new Response(t("guides.notFound"), { status: 404 });
}

// meta（root ローダーの値を matches 経由で取る）
export const meta: Route.MetaFunction = ({ matches }) => {
  const t = createTranslator(localeFromMatches(matches));
  return [{ title: t("home.title") }];
};
```

## 切替UI

- **デスクトップ**: ヘッダー右の地球アイコン（`app/components/locale-switcher.tsx`）
- **モバイル**: メニュー内、テーマ切替の下にセグメント切替で並ぶ

どちらも `useSetLocale()`（`app/hooks/use-locale.tsx`）を使う。**文言はサーバー側で決まるため、クライアント state を書き換えるだけでは切り替わらない。** Cookie を `/api/set-locale` へ POST して保存し、再検証で全ローダーを新しいロケールで再実行させる。

> `/api/set-locale` は `app/routes.ts` への登録が必要（このリポジトリはルートを手動定義する）。登録漏れがあると切替が 404 になる。

## 英語化の状況

**メッセージカタログ（`pages-ja.ts` / `pages-en.ts`）は全キー英訳済み**。`app/lib/__tests__/locale.test.ts` の「翻訳カバレッジ」テストが、日本語にキーを足して英語を忘れた場合に落ちる。

`t()` を直接呼ぶファイルは**ゼロ**（コンポーネントは `useT()`、ローダー/meta は `createTranslator(...)`）。この状態を保つこと — `import { t } from "@/lib/messages"` を新たに書くと、その画面だけロケールに追従しなくなる。

### 残っている日本語

**UI 文言のハードコードは解消済み**。英語ロケールで各ページを取得して日本語文字列を走査した結果、残るのは利用者が入力したデータ（ランナー名・ガイトタイトル等）だけ。

意図的に日本語のまま残しているもの:

- `app/components/guide-editor/extensions/toggle-list.ts` の `summaryText` 既定値（`"トグル"`）。**保存される本文の一部**であり、ロケールで変えると同じガイドの出力が環境によって変わる。表示側のプレースホルダのみ翻訳済み
- `app/lib/preset-utils.ts` のプリセット説明（`"インポートされた設定から自動作成されたプリセット"` など）。**DB に保存される値**なので同上
- `app/lib/game-languages.ts` の言語名。Minecraft 側の表記をそのまま出す
- `app/lib/email.server.ts` のフィードバック通知メール。宛先は運営のみで利用者は見ない
- `app/lib/external-stats.ts` の `error` 文字列。表示されずフラグとしてのみ使われる

進め方は既存と同じ: `pages-ja.ts` にキーを起こし、`pages-en.ts` に英訳を足し、呼び出し側を `t()` 経由にする。モジュール直下の定数に文言を持つ場合は、**キーだけ持たせて描画時に解決する**（ロケールはモジュール評価時に未確定のため）。

> **落とし穴 1**: `import { t } from "./messages"` のように**相対パス**で直接 import すると、常に日本語を返す関数を掴んでしまう。型エラーにならないので気づけない（実際 `keybindings-stats.server.ts` と `search-craft-templates.ts` で踏んだ）。サーバー側は `createTranslator(resolveLocale(request))`、集計結果を返す関数は**翻訳キーのまま返して描画側で解決する**。

> **落とし穴 2**: `createRoot()` で**アプリのツリー外にマウントする UI** では `useT()` が効かない。`LocaleContext` の既定値（`ja`）にフォールバックし、これも型エラーにならない。スラッシュメニュー（`guide-editor/slash-command/renderer.ts` が `document.body` に別ルートを作る）が該当し、`t` を props で渡して解決している。TipTap の `ReactNodeViewRenderer` はエディタのツリー内へポータルするため影響しない。

> **落とし穴 3**: ルートが 1 つも一致しないと **root ローダーが実行されない**ため、ロケールが既定（`ja`）のまま root の ErrorBoundary が描画される。`routes/not-found.tsx`（`route("*", ...)`）で一度マッチさせて root ローダーを走らせてから 404 を投げ直すことで解決している。このキャッチオールは必ず `app/routes.ts` の最後に置くこと。

### 利用者が入力したデータのロケール対応

利用者が書いた内容は翻訳しないが、**表示名だけは利用者自身が英語版を登録できる**。

- `users.displayNameAlphabet`（`/me/edit` の「表示名（アルファベット表記）」）
- `ja` 以外のロケールでは `displayName` の代わりに使う。未入力なら `displayName` にフォールバック
- 解決は `pickDisplayName(user, locale)` / `getLocalizedDisplayName(user, locale)`（`app/lib/slug.ts`）
- 詳細は `docs/profiles.md`「表示名のアルファベット表記」

> **落とし穴 4**: ロケール解決は**描画直前**に行う。`home-user-data.server.ts` /
> `paces-feed.server.ts` / `youtube-cache.ts` のキャッシュはリクエスト間で共有されるため、
> 解決済みの名前を入れると最初に温めた閲覧者のロケールが他の全員に配られる。
> これらは両方の名前を持ち回り、コンポーネント側で `useLocale()` を使って解決している。

### 翻訳しないもの

- **利用者が書いた内容**（ガイド本文・プロフィール・テンプレート名など。表示名の英語表記のみ上記の例外）
- **Markdown ドキュメントの本文**: `/developers/api` と `/developers/changelog` は `app/content/api.md` / `changelog.md` をそのまま描画する。ページの枠（見出し・パンくず）は翻訳済みだが、**中身は日本語のまま**。翻訳するなら文言ではなくファイルをロケール別に持つ必要がある
- **読み込み画面の Minecraft スプラッシュ由来の文言**（`navigation-progress.tsx` の `SPLASH_TIPS`）。元ネタの語感がすべてなので、どのロケールでも原文のまま出す
- **言語の自称表記**（`common.langJaJp` など）。英語UIでも「日本語」と出したほうが分かりやすい
