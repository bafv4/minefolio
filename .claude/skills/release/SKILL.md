# リリース（Changelog 作成 + バージョン更新）

**バージョン番号と changelog は、この作業の指示があったときにだけ更新する。**
通常の機能追加・修正のコミットでは changelog に都度書かない（`CLAUDE.md`「バージョン管理・Changelog」）。

## 前提の確認

- **バージョン番号はユーザーが指定する。** 指定がなければ聞く（推測で決めない）。
- リリース日も指定があればそれに従う。なければ当日。
- 未リリースのエントリが changelog の先頭に残っていることがある。その場合は
  **新バージョンに統合する**（過去に「v1.8.1 は未リリースなので統合」「v1.8.3 以降を置換」の指示あり）。

## 手順

1. **差分を全件精査する。**

   ```bash
   git fetch origin
   git log --no-merges --oneline origin/main..dev
   ```

   件数が多いときは `git log --no-merges origin/main..dev --stat` や、
   気になるコミットを `git show` で個別に確認する。**全件見る**（要約コミットだけ拾わない）。

2. **利用者目線で挙動が変わるものだけ抽出する。**

   | 載せる | 載せない |
   |---|---|
   | 画面・操作・表示が変わる | 内部リファクタ・型修正 |
   | 新機能・新ページ・新項目 | テスト追加 |
   | ユーザーが遭遇していた不具合の修正 | docs / CLAUDE.md / .claude 配下の更新 |
   | 制限・既定値の変更 | 依存パッケージ更新（挙動が変わらないもの） |
   | パフォーマンス改善で体感が変わるもの | CI・ビルド設定 |

3. **プライバシーポリシー・利用規約の改定要否を判定する。**

   対象は `app/content/privacy.md`（プライバシーポリシー）と `app/content/terms.md`（利用規約）。

   まず、コミット時に立てられたフラグ（`commit` スキルの `Policy-Revision:` トレーラー）を確認する:

   ```bash
   git log --no-merges origin/main..dev --grep "^Policy-Revision:" --format="%h %s%n%(trailers:key=Policy-Revision)"
   ```

   フラグ付きコミットは必ず改定対象として精査する。**フラグが無くても改定不要とは判断しない**
   （付け漏れがありうる）。手順 1 の差分に次のいずれかが含まれる場合は改定が必要:

   | 差分の内容 | 改定対象 |
   |---|---|
   | 外部サービスへの送信の追加・削除（サーバーからの送信も、埋め込み・CDN・フォント等のブラウザからの直接送信も含む） | privacy「外部サービスへの情報送信・委託」の表 |
   | 取得する情報の追加・変更（新しい登録項目・自動取得項目） | privacy「取得する情報」「利用目的」 |
   | Cookie / localStorage の追加・廃止 | privacy「Cookie 等について」 |
   | 公開範囲・データ削除・エクスポート等、ユーザーによる管理機能の変更 | privacy「ユーザーによる情報の管理」 |
   | 新しい投稿コンテンツ種別・公開面の追加 | terms「定義」「投稿コンテンツの権利」、privacy「公開される情報」 |
   | 禁止事項・コンテンツ削除/アカウント停止の基準に関わる機能 | terms「禁止事項」「コンテンツの削除・アカウントの停止」 |

   - 該当なしならこの手順はスキップし、手順 4 のドラフト提示時に「ポリシー改定は不要」と一言添える。
   - 判定に迷う場合は「改定案を提示して、ユーザーに要否を委ねる」に倒す（黙って見送らない）。

4. **changelog 本文のドラフト（＋ポリシー改定がある場合はその改定ドラフト）を作成し、チャットに全文提示してユーザーの承認を得る。**

   - **この時点ではファイルを一切変更しない**（changelog・privacy/terms・package.json・docs すべて）。
   - プランモードの承認と同じ位置づけ: ドラフト全文と、続けて行う変更
     （バージョン更新・docs 追随の有無・コミットメッセージ）を提示し、
     「この内容で進めてよいか」を明示的に確認する（`AskUserQuestion` を使ってよい）。
   - ポリシー改定ドラフトは changelog と同様に**変更後の文面をそのまま提示**する。
     改定箇所ごとに「対象ファイル・対象セクション・改定前 → 改定後」の形で示し、
     全文の再掲は不要（変更セクションのみでよい）。
   - ポリシーを改定する場合、changelog ドラフトの「その他」に
     「**プライバシーポリシー／利用規約を改定しました。**」の項目を必ず入れる
     （ポリシー本文の「重要な変更を行う場合は、本サイト上で告知します」との整合のため）。
   - 修正指示があればドラフトに反映し、再提示して改めて承認を得る。
   - **承認が得られるまで手順 5 以降に進まない。**

   ドラフトは既存フォーマットを厳守:

   ```markdown
   ## vX.Y.Z（YYYY/MM/DD）

   ### <機能ドメイン名>

   - **結論を一文で、太字で。** 必要なら補足を続ける（1〜2文）。
   ```

   - セクション名は機能ドメイン（例: ホーム / ガイド / プロフィール / 操作設定一覧 /
     デバイス設定 / 表示言語 / 不具合修正 / その他）。実際に変更があったものだけ立てる。
   - **不具合修正**と**その他**は最後に置く。
   - 各項目は「**〜しました。**」で終わる太字の結論から始める。
   - **なるべく短く簡潔に。** 冗長にしない。実装の内部事情は書かない。
   - ユーザーが誤解しそうな点は明記する（例: 「ご自身で書かれた内容は翻訳されません」
     「変換はブラウザ内で完結し、動画そのものはアップロードされません」）。

5. **（承認後）`app/content/changelog.md` の先頭に、承認されたドラフトを追記する。**

6. **（ポリシー改定がある場合）承認された改定を `app/content/privacy.md` / `app/content/terms.md` に反映する。**

   - 各ファイル末尾の日付欄を更新する: `制定日` はそのまま残し、
     `最終改定日: YYYY年MM月DD日` を追記（既にあれば日付を更新）する。
   - 改定はリリースコミットに混ぜず、**手順 9 の直前に別コミット**にする
     （1コミット1トピックの分割原則）。例:

     ```
     docs(policy): vX.Y.Z に伴いプライバシーポリシーを改定（外部送信先の追加）
     ```

7. **`package.json` の `version` を更新する。**

8. **仕様変更が `docs/` に未反映なら追随させる**（`docs/` の該当ファイル、必要なら `.claude/rules/`）。

9. **コミットする。**

   ```
   chore(release): vX.Y.Z（チェンジログ作成・バージョン更新）
   ```

## デプロイ

- **本番 = `main` ブランチ。** dev → main の PR マージで反映される。
- **dev 環境 = `dev` ブランチ**のプレビューデプロイ。
- リリースコミット後に push / PR 作成をするかは、指示に従う（自動では行わない）。
  PR を作る場合は `/create-pr` スキルを使う。
