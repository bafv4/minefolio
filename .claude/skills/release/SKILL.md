# リリース（Changelog 作成 + バージョン更新）

**バージョン番号と changelog は、この作業の指示があったときにだけ更新する。**
通常の機能追加・修正のコミットでは changelog に都度書かない（`CLAUDE.md`「バージョン管理・Changelog」）。

## 前提の確認

- **バージョン番号はユーザーが指定する。** 指定がなければ聞く（推測で決めない）。
- リリース日も指定があればそれに従う。なければ当日。
- 未リリースのエントリが changelog の先頭に残っていることがある。その場合は
  **新バージョンに統合する**（過去に「v1.8.1 は未リリースなので統合」「v1.8.3 以降を置換」の指示あり）。

## 手順

1. **差分を全件精査する。**

   ```bash
   git fetch origin
   git log --no-merges --oneline origin/main..dev
   ```

   件数が多いときは `git log --no-merges origin/main..dev --stat` や、
   気になるコミットを `git show` で個別に確認する。**全件見る**（要約コミットだけ拾わない）。

2. **利用者目線で挙動が変わるものだけ抽出する。**

   | 載せる | 載せない |
   |---|---|
   | 画面・操作・表示が変わる | 内部リファクタ・型修正 |
   | 新機能・新ページ・新項目 | テスト追加 |
   | ユーザーが遭遇していた不具合の修正 | docs / CLAUDE.md / .claude 配下の更新 |
   | 制限・既定値の変更 | 依存パッケージ更新（挙動が変わらないもの） |
   | パフォーマンス改善で体感が変わるもの | CI・ビルド設定 |

3. **changelog 本文のドラフトを作成し、チャットに全文提示してユーザーの承認を得る。**

   - **この時点ではファイルを一切変更しない**（changelog・package.json・docs すべて）。
   - プランモードの承認と同じ位置づけ: ドラフト全文と、続けて行う変更
     （バージョン更新・docs 追随の有無・コミットメッセージ）を提示し、
     「この内容で進めてよいか」を明示的に確認する（`AskUserQuestion` を使ってよい）。
   - 修正指示があればドラフトに反映し、再提示して改めて承認を得る。
   - **承認が得られるまで手順 4 以降に進まない。**

   ドラフトは既存フォーマットを厳守:

   ```markdown
   ## vX.Y.Z（YYYY/MM/DD）

   ### <機能ドメイン名>

   - **結論を一文で、太字で。** 必要なら補足を続ける（1〜2文）。
   ```

   - セクション名は機能ドメイン（例: ホーム / ガイド / プロフィール / 操作設定一覧 /
     デバイス設定 / 表示言語 / 不具合修正 / その他）。実際に変更があったものだけ立てる。
   - **不具合修正**と**その他**は最後に置く。
   - 各項目は「**〜しました。**」で終わる太字の結論から始める。
   - **なるべく短く簡潔に。** 冗長にしない。実装の内部事情は書かない。
   - ユーザーが誤解しそうな点は明記する（例: 「ご自身で書かれた内容は翻訳されません」
     「変換はブラウザ内で完結し、動画そのものはアップロードされません」）。

4. **（承認後）`app/content/changelog.md` の先頭に、承認されたドラフトを追記する。**

5. **`package.json` の `version` を更新する。**

6. **仕様変更が `docs/` に未反映なら追随させる**（`docs/` の該当ファイル、必要なら `.claude/rules/`）。

7. **コミットする。**

   ```
   chore(release): vX.Y.Z（チェンジログ作成・バージョン更新）
   ```

## デプロイ

- **本番 = `main` ブランチ。** dev → main の PR マージで反映される。
- **dev 環境 = `dev` ブランチ**のプレビューデプロイ。
- リリースコミット後に push / PR 作成をするかは、指示に従う（自動では行わない）。
  PR を作る場合は `/create-pr` スキルを使う。
